# 多屏渲染性能基准（T3-2）

> 一句话：**多屏是线性代价，不是指数代价** —— 每多一块屏，帧成本按一块屏的
> 成本加上去（1600×900、200 行场景下约 4.8 ms/屏/帧），没有出现"窗口数一多
> 就雪崩"的二次项。真正贵的两处不在多屏，而在**单帧本身**（软件光栅化 1600×900
> 约 4.8 ms，意味着 60 fps 的 16.6 ms 预算里只剩 1/3 给应用逻辑）和**长列表
> 不用虚拟化**（10 万行全量布局是 1.9 s，虚拟化后 77 µs，差 24000 倍）。

## 1. 口径

| 项 | 说明 |
|---|---|
| 场景 | 每块屏一个窗口（1600×900）：顶栏 + 左栏（320 宽）+ 右栏滚动列表（200 行 `list-item`）。各窗口共用同一棵树形，变量只有**窗口数** |
| 渲染路径 | 生产同款 `app.redraw()`（Layout + Draw + 焦点环 + ShowRegions），只是 ShowRegions 落在假 Surface 上 |
| 事件路径 | `Surface.push` → `appForSurface` 路由 → `app.processEvents` → 命中测试 → 悬停链差分 → 标脏；**不含渲染**（渲染成本见第 2 节，二者相加即"事件 → 画面"） |
| 显示环境 | **无需 X11/GPU**：不导入任何平台后端，不建真窗口，CI 无头照常跑 |
| 计时 | 外部 `go test -bench`，`-benchtime 10x`；绝对值随机器，**只信同机趋势** |

## 2. 实测数字

环境：go1.27.3 / linux-amd64 / 32 核 / commit 见 `bench-results/multiscreen-20261028T0250Z.json`。

### 2.1 多屏同渲染（一帧的总成本 vs 每屏成本）

| 窗口数 | ns/op | ns/frame（每屏） | 相对 1 屏 |
|---:|---:|---:|---:|
| 1 | 4,884,619 | 4,884,619 | 1.00× |
| 2 | 10,162,505 | 5,081,252 | 1.04× |
| 3 | 14,309,392 | 4,769,797 | 0.98× |
| 4 | 18,942,664 | 4,735,666 | 0.97× |

**结论**：每屏成本基本恒定（4.8 ms ± 5%），总成本 = 屏数 × 单屏成本。没有固定
摊销项随屏数增长（说明窗口注册表查找、焦点环、脏区汇总都不是 O(N) 扫描）。
也就是说 **4 屏 = 19 ms/帧 ≈ 52 fps**，瓶颈是单屏光栅化速度，不是多屏调度。

### 2.2 「只有一屏变」也不便宜

| 窗口数 | 全屏都变 | 1 整帧 + (N−1) 局部 | 差异 |
|---:|---:|---:|---:|
| 1 | 4.98 ms | 4.98 ms | — |
| 2 | 10.16 ms | 9.63 ms | −5% |
| 4 | 18.94 ms | 19.98 ms | +5% |

**结论（值得注意）**：真实多屏应用的帧分布是"一屏变、其余不动"，但实测这条
路径**并不比全帧便宜**（差异在噪声内）。原因在假 Surface 的 `ShowRegions` 仍按
整帧拷贝 —— 也就是说这个基准量的是"内核算多快"，**没有**量到"后端真上屏多快"。
真机上的脏区收益体现在传输/上屏，不在本基准里；要看上屏成本得用 GPU/真窗口
路径（见 `gfx/present_bench_test.go`，需 `-tags gpu` 且 `linux`）。

### 2.3 多窗口下的单条事件成本

| 存活窗口数 | ns/op（一次 MouseMove：路由 + 命中 + 悬停差分 + 标脏） |
|---:|---:|
| 1 | 1,786,313 |
| 2 | 2,415,158 |
| 4 | 2,039,820 |

**结论**：与窗口数无关（2/4 屏的差异是噪声，2 屏那次偏高是首次运行页缓存冷）。
但**绝对值偏高：一次 MouseMove ≈ 2 ms**，而一帧才 4.8 ms —— 鼠标连发时事件处理
会吃掉接近半帧预算。悬停差分作用在 200 行上是 O(行数)，这是后续优化点（命中
测试应从"线性遍历可见行"改为"按 y 二分/空间索引"）。

### 2.4 vlist 长列表滚动一屏

| 口径 | 1 千行 | 1 万行 | 10 万行 |
|---|---:|---:|---:|
| 虚拟化滚动一屏（`VlistScrollScreen`） | 27.7 µs | 52.4 µs | — |
| 虚拟化滚动 300px（`VlistScroll/vlist`） | 238 µs | 133 µs | 77 µs |
| **不虚拟化**全量布局（`VlistScroll/full`） | 11.0 ms | 152 ms | 1,900 ms |

**结论**：虚拟化后成本与行数**基本脱钩**（每轮只物化 13 行），10 万行仍是
微秒级；不虚拟化则是 O(N) 灾难（10 万行 1.9 s ≈ 0.5 fps）。1 千 → 1 万那 1.9×
的增长来自每轮重算 `scrollMaxOffset`（O(N) 求和），可优化为增量维护，但量级
不影响结论。

## 3. 复现

```bash
# 全部（约 35 s）
go test ./gfx -run '^$' -bench 'MultiScreen|CrossScreenEvent|VlistScroll' -benchtime 10x

# 只跑多屏渲染
go test ./gfx -run '^$' -bench 'MultiScreen' -benchtime 10x
```

无头环境直接可跑，不需要 `DISPLAY`、不需要 xvfb。

## 4. 已知盲区（诚实边界）

1. **不含上屏**。假 Surface 的 ShowRegions 是内存拷贝，量不到 X11/GPU 的传输与
   呈现成本。真上屏请看 `present_bench_test.go`（`-tags gpu`）。因此"局部脏区
   不比全帧快"这个结论只对**内核计算**成立。
2. **跨屏点击 / 滚轮两条口径暂未纳入**。连续轮次下假 Surface 的事件队列**每轮
   漏消费一条**，约 8 轮后 `push` 阻塞、基准挂死（1/2/3/5 轮都正常，10 轮挂死，
   ns/op 还随轮次线性上升）。这是**基准脚手架**的问题（`helpers_test.go` 的
   fakeSurface / movableSurface 事件通道），不是内核路径的问题；定位后再补，
   不拿一个会挂死的基准进 CI。
3. **单屏 4.8 ms 是软件光栅化的结果**，不含 GPU 绘制（内核目前只把 GPU 用于
   上屏合成，见 `docs/video-decision.md`）。上 GPU 后的数字会完全不同。
4. 每屏尺寸固定 1600×900；4K 单屏的成本见 `present_bench_test.go`（不在本文件）。
5. 事件基准只量 MouseMove 一条路径；键盘/触摸/滚轮路径未量。

## 5. 与既有基准的分工

- `gfx/present_bench_test.go`：**上屏**成本（X11/CPU 呈现、4K、脏区），需显示环境/构建标签。
- `gfx/vlist_bench_test.go`：滚动 300px 的虚拟化 vs 全量对比。
- 本文件：**多屏维度**（屏数 × 帧成本、多窗口事件成本）+ 一万行滚整屏。
