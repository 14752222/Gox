gfx: 批次 H —— P3-4 原生系统对话框（gx/dialog）

封装系统对话框，注册为新内置模块 gx/dialog（gfx/dialog.go）。
API 全部 async（返回 Promise），脚本用 await：

  alert(msg, title?)                        → Promise<undefined>
  confirm(msg, title?)                      → Promise<bool>
  openFile({title, filter})                 → Promise<string | null>

实现取舍：刻意不走"goroutine 弹框 + channel 回传"的方案，改为
"同步落地 + 异步外观" —— 两条理由：
  1) 以主窗口为 hwndOwner 的 MessageBoxW 自带模态消息泵（Windows
     归一到调用线程的消息队列），重绘/拖动照常，不需要额外线程；
  2) 在 goroutine 里 resolve 是红线：invokePromiseCallbacks 是同步的，
     会在那个 goroutine 里跑 JS 回调，违反"脚本/泵/回调同线程"。
所以 resolve 统一经 resolveDeferred = SetTimeout(...,0) 投回事件循环
（与 stdlib/http.go 的 dispatchToLoop 同款）。

能力仍走可选接口 nativeDialogHost（第四个先例，前三个是 clipboardHost /
capturer / imeController）：Surface 接口不扩，win32 走 MessageBoxW +
GetOpenFileNameW，其他后端降级（内容写 stderr；confirm 取 true、
openFile 取 null —— 无人值守时静默跳过副作用比"照做"更难排查）。

OPENFILENAMEW 的 Win64 布局（任务书标为高风险）已消除：gfx/win32/
dialog_test.go 用 unsafe.Offsetof 逐字段钉死偏移（0/8/24/48/56/64/96/104），
Sizeof 断言 >=152 && <=512 && %8==0（实测 160）⇒ 三个 API 全部交付，
不必按任务书的退路只做 alert/confirm。

win32 三个易错点：
  - OFN_NOCHANGEDIR 不能省：否则对话框会把进程工作目录改到用户选的
    目录，而 <image src="./a.png"> 相对进程工作目录解析 ⇒ 相对路径全错；
  - 过滤串必须双 NUL 结尾，描述里混 NUL 会提前截断整串；
  - utf16Ptr 返回切片 + runtime.KeepAlive，防 GC 悬空。

测试：gfx 顶层新增 10 例、gfx/win32 新增 4 例（布局/过滤串/指针/接口
满足性），顶层用例数 211 → 222。过程中定位并记录两个必守点：
  - Pump 处理到 EventClose 会立刻返回 false，事件循环退出时把排在后面的
    定时器任务一起丢掉（症状：Promise 的 then 永不执行）⇒ 新增
    drainWithClose：前几轮不推 close，收工由外部事实 done() 驱动；
  - GUI 模式下 runTimersLoop 无定时器时传 maxWait=0（语义：无限期等），
    假 Surface 会当 10s 睡 ⇒ 测试泵必须把 wait 钳到有限值（10ms）。
另修一处顺序依赖（TestDialogFallsBackWithoutBackend 依赖 ambient
activeApp），并加 bareSurface 用例覆盖"挂了窗口但 Surface 未实现可选接口"。

演示：testdata/dialog_native_demo.js（三个按钮全走 await）。顺带发现
运行时只支持 async function、不支持 async () => {}（parseAsyncExpression
对非 function 直接 addError），演示改用 async function () {...} 并写进文档。
